# 요청량 최적화 5단계 — 경기 상태별 조회 주기

확인일: 2026-10-21 21:53 KST. 비교 기준은 4단계 커밋 `f5e191bf3fbaa71eddc3f0abe093228d8da0f08d`, 작업 브랜치는 `codex/request-optimization`이다. 검토용 PR은 https://github.com/QuietJ00/Quartermate/pull/24 이며 main 병합·운영 배포는 수행하지 않았다.

## 적용한 주기

| 현재 팀 경기 상태 / 화면 | room 자동 GET 주기 |
|---|---:|
| 진행 중(`live`), 모든 화면 | 3초 |
| 일시정지·쿼터 사이 대기, 상태가 여전히 `live` | 3초 |
| 예정·종료 경기, 일정·선수단·설정·경기 준비 | 15초 |
| 예정·종료 경기, 시즌 분석 | 30초 |
| 브라우저 숨김, 저장 중, 탈퇴 창 | 정기 조회 없음 |

진행 중 여부를 화면 종류보다 먼저 판단한다. 시즌 분석이나 선수단을 보고 있어도 팀의 현재 경기가 진행 중이면 3초를 유지한다. 정상 응답과 화면을 유지하는 조건에서 다른 기기의 경기 시작은 일반 화면에서 최대 약 15초, 시즌 분석에서 약 30초에 감지하며, 네트워크 응답 시간은 추가된다. 감지한 다음 조회부터 3초로 전환한다. 종료를 감지하면 해당 화면의 15초/30초로 돌아간다.

로컬 경기 시작·종료·저장은 기존 응답을 즉시 적용한다. 투표 성공 뒤의 즉시 room 재조회도 유지한다. 화면 복귀 시 주기 만료를 기다리지 않고 즉시 조회하며, visibilitychange와 focus가 함께 오면 기존 조정기로 한 번으로 합친다. HTTP 409 복구와 명시적 조회도 느린 정기 주기를 기다리지 않는다.

변경은 `app/page.tsx`의 room 타이머에 한정했다. 주기 또는 팀 코드가 바뀌면 이전 타이머를 정리한다. 같은 상태의 새 응답·revision만으로 타이머를 다시 시작하지 않는다. 서버 API·DB·인증·배포 설정은 그대로다. 연계 대회 15초, 대회 상세 5초, 내 팀 15초 조회도 기존 주기를 유지한다. 오류 시에도 선택된 주기로 재시도하며 GET 15초 제한·중복 제거·오래된 응답 차단을 유지한다.

## 4단계 대비 측정

실제 React 컴포넌트를 합성 fetch·jsdom·가상 시계에서 60초 실행했다. 초기 로딩·화면 진입 요청을 제외한 안정 상태의 **클라이언트 자동 API GET 수**다. 일정·시즌 분석에는 연계 대회 GET도 포함한다.

| 화면 | 이전 / 분 | 변경 후 / 분 | 감소율 |
|---|---:|---:|---:|
| 비진행 경기 일정 | 24 | 8 = room 4 + 연계 대회 4 | 66.7% |
| 비진행 선수단 | 20 | 4 | 80% |
| 비진행 시즌 분석 | 24 | 6 = room 2 + 연계 대회 4 | 75% |
| 진행 중 경기 일정 | 24 | 24 | 기존 속도 유지 |
| 진행 중 라인업 | 20 | 20 | 기존 속도 유지 |
| 내 팀 | 8 | 8 | 유지 |
| 대회 상세 | 12 | 12 | 유지 |

숨김 상태 60초의 자동 GET은 모든 측정 화면에서 0회다. 팀 화면 복귀는 room GET 1회, 내 팀 복귀는 account/workspace 각 1회다. room 자체만 보면 비진행 일반 화면 80%, 시즌 분석 90% 감소하지만, 연계 대회 요청을 포함한 화면 전체와 구분해야 한다.

이 비율은 동일한 사용 패턴의 정기 조회 부분에 적용한다. 이 측정만으로는 운영 전체 Worker 요청·D1 읽기·CPU 비용이나 무료 요금제로 수용할 사용자 수가 얼마나 달라지는지 알 수 없다. 최초 로딩, 저장·투표, 자산, SSR, 대회 화면 비중과 실제 동시 접속을 함께 측정해야 최종 수용량을 갱신할 수 있다.

## 검증

새 적응 주기 시나리오 **16개**, 기존 요청량·저장 보호 시나리오 **20개**, 기존 경합 시나리오 **16개를 예정/진행 중 상태에서 각각 실행한 32회**가 모두 통과했다.

- 다른 기기의 시작을 15초/30초에 감지한 뒤 3초로 전환하고, 종료 후 15초/30초로 복귀.
- 진행 중 선수단·시즌 분석·설정과 일시정지 상태에서도 3초 유지.
- 내 기기에서 시작·최종 쿼터 종료 시 API 응답 즉시 반영하고 새 주기로 전환.
- 저장 중 15초 주기 억제, 응답 즉시 표시. 투표 후 15초를 기다리지 않는 즉시 room 재조회.
- 숨김 중 시작된 경기를 복귀 즉시 반영하고 복귀 이벤트 중복 제거.
- 같은 상태 응답이 다음 조회를 미루지 않음. 화면 전환 반복 시 옛 타이머가 남지 않음.
- 500 오류 후 15초/30초 재시도와 정상 상태 회복, 시즌 분석 GET 시간 제한 후 재시도.
- 저장 전 늦은 200/401/403, 권한 회수·동일 revision·관리 창 정리, 로그아웃·실패·초기 로딩 경합, 팀 A/B 왕복, StrictMode, 다른 창 로그인 인식 보호 유지.

검사: typecheck, 단위 **210개**, 백엔드 **98개**, 마이그레이션 스키마 및 스냅샷 **20개**, cf:build, cf:verify, built Worker 로컬 HTTP **19개** 통과. 측정 스크립트 구문 검사, git diff --check, 소스·이력 감사 고신뢰 탐지 0건. Home ESLint는 변경 전후 오류 3/경고 11로 기존 개수와 규칙이 같다. 이 비교로 전체 저장소의 lint 통과 여부를 판단할 수 없다.

원본 결과는 `request-optimization-stage5-results.json`에 주기 전환·화면별 요청량·두 상태의 경합 결과를 함께 저장했다. 4단계 결과 파일은 보존했다. 기존 빠른 주기의 요청 중첩 회귀는 진행 중 fixture로 실행하고, 예정 상태 경합은 새 15초 주기로 실행하도록 측정 도구를 조정했다. clock API는 합성 응답으로 처리하므로 이 검사가 서버 시계 로직 자체를 검증하지는 않는다. 서버 권한·시계 처리는 기존 백엔드 및 built Worker 검사로 함께 확인했다.
