# 요청량 최적화 2단계 — 수정 전 측정

확인일: 2026-10-21 21:05 KST. 측정 대상 소스는 4765a61117ee5c44ea68e7f9d65e91f35ecdfb3b이며 앱 코드는 운영 기준 4cbf4c2549a0b9a8f3737c107da28412041b4dc6과 같다.

## 방법과 범위

`scripts/measure-client-requests.mjs`가 기존 Home, TeamHub, TournamentHub, TournamentPage와 실제 하위 컴포넌트를 esbuild로 묶어 React에 마운트한다. jsdom의 DOM, 가상 시계와 합성 fetch 응답을 사용한다. 갱신 함수를 복사해 재구현한 시뮬레이션은 아니다. StrictMode를 사용하지 않으며 React act를 위해 개발 모드로 번들한다.

계정·팀·경기는 모두 스크립트가 만든 합성 데이터다. 서버, 실제 카카오 로그인, Cloudflare 자원 및 운영 DB/R2에는 연결하지 않는다. JS/CSS/이미지 파일 로딩, SSR/RSC 요청, 네트워크 지연의 실제 분포, 브라우저별 타이머 제한, DB/CPU 사용량과 레이아웃은 측정에 포함되지 않는다. 따라서 아래 수치는 **클라이언트 API 호출의 재현 측정**이며 운영 전체 트래픽의 실측치가 아니다. 응답 지연·실패는 별도 시나리오에서 명시적으로 주입했다.

환경: Node 24.21.0, React 19.2.6, esbuild 0.28.0, jsdom 30.1.3, fake-timers 15.4.0. 상세 카운터와 요청 타임라인은 `request-optimization-measurements.json`에 있다.

## 화면별 정기 요청

초기 로딩이 끝난 뒤 카운터를 초기화하고 가상 시간 60초를 진행했다. 서버 데이터가 변하지 않는 조건이다. 시간당 값은 60초 측정값을 60배 한 값이며 초기 로딩·사용자 조작은 제외한다.

| 화면 | 60초 호출 | 시간당 환산 | 호출 구성 |
|---|---:|---:|---|
| 내 팀 | 8 | 480 | account 4 + workspace 4 |
| 팀 경기 일정 | 24 | 1,440 | room 20 + 연동 대회 4 |
| 팀 선수단 관리 | 20 | 1,200 | room 20 |
| 팀 시즌 분석 | 24 | 1,440 | room 20 + 연동 대회 4 |
| 진행 중 경기의 일정 화면 | 24 | 1,440 | room 20 + 연동 대회 4 |
| 진행 중 경기의 라인업 화면 | 20 | 1,200 | room 20; 경기 시계 틱은 추가 API 호출 없음 |
| 대회 상세 | 12 | 720 | tournaments 12 |
| 대회 목록 | 0 | 0 | 정기 갱신 없음; 진입 시 tournaments + workspace 각 1 |

각 화면을 숨긴 뒤 60초 동안 진행했을 때 정기 API 호출은 모두 0건이었다. 이는 기존 정상 동작이며 후속 변경에서 유지해야 한다.

경기 일정의 투표 명단은 경기별 마운트 및 revision 변경에 따라 추가 조회한다. 이번 한 경기·revision 고정 조건의 정기 카운터를 경기 수나 변경 빈도가 다른 상황의 상한으로 사용하지 않는다.

## 재현한 중복·비효율

### 화면 복귀 이벤트 중복

숨김 상태에서 visible로 바꾼 뒤 `visibilitychange`와 `focus`를 차례로 전달했다.

- 내 팀: account 2회 + workspace 2회 = 총 4회. 한 번의 load에 해당하는 2회보다 두 배다.
- 팀 화면: room 2회. 같은 팀을 연속 조회한다.
- 대회 상세: 즉시 요청 0회. 다음 5초 주기까지 복귀 갱신을 기다린다.
- 대회 목록: 즉시 요청 0회. 자동 복귀 갱신 자체가 없다.

실제 브라우저에서 항상 두 이벤트가 함께 발생한다는 뜻은 아니다. 두 이벤트가 발생하는 조건에서 중복 조회가 가능한 것을 재현했다. 연동 대회 조회는 팀 화면의 복귀 즉시 조회 대상에도 포함되지 않는다.

### 느린 조회 중 추가 조회

room 응답을 4.5초 지연시켰다. 첫 조회는 3초에 시작해 7.5초에 끝나지만 다음 조회는 6초에 시작했다. 9초에도 추가 조회가 시작됐으며 room 요청 최대 2개가 겹쳤다. 이전 조회가 진행 중이어도 3초 setInterval이 새 요청을 시작한다.

### 오류 이후에도 고정 주기 요청

room에 합성 HTTP 500 응답을 반환했다. 15초 동안 3·6·9·12·15초에 room 요청 5회가 이어졌다. 오류 시 재시도 간격을 늘리는 동작은 없다.

### 초기 로딩에서 내 팀이 잠시 마운트됨

팀 URL로 바로 진입했을 때 Home은 room이 도착하기 전 TeamHub를 렌더한다. 합성 조건에서 초기 API 9회를 관찰했고 account와 auth/config가 각각 두 번 호출됐다. 이는 StrictMode 이중 실행이 아니라 부모 초기 로딩과 자식 TeamHub 로딩이 겹치는 구조다. 초기 오류·로그인 화면의 표시를 보존하면서 별도로 검토할 최적화 후보다.

## 유지해야 할 기존 보호장치

1. **저장 중 정기 갱신 억제:** PUT을 7초 지연시키고 첫 6초를 관찰했다. PUT 1회, room GET 0회였다.
2. **저장 전 조회의 늦은 응답 차단:** revision 1 GET을 3초에 시작하고 같은 시점에 이름 변경 PUT을 시작했다. revision 2 PUT은 4초에 완료하고 옛 GET은 7.5초에 완료했다. 화면에는 저장한 새 이름이 유지됐다. 기존 revision 비교가 이 케이스를 보호한다.
3. **숨김 상태 정기 요청 중단:** 측정한 8개 화면/상태에서 60초간 0회.

이 결과는 동일 revision의 권한·가입 신청 변경, 팀 전환 왕복, 로그아웃, 실제 두 계정 동기화까지 통과했다는 뜻은 아니다. 해당 회귀 시나리오는 4·6단계에서 별도로 검증한다.

## 재현 명령

아래는 2단계 커밋 `a9aa64750c5c1a1ef0cec6128a447d1e42d5397f`에서 실행한 명령이다. 이후 3단계 브랜치의 스크립트는 중복 제거 후 기대값과 추가 시나리오를 검사한다. 2단계 원본 결과 JSON은 그대로 보존한다.

일반 프로젝트 의존성이 설치된 작업 폴더에서 실행한다. 아래 측정 도구만 별도의 무시되는 work 디렉터리에 설치하며 앱 package.json/잠금 파일을 변경하지 않는다.

```sh
npm install --prefix work/request-measurement-runtime --no-audit --no-fund --package-lock=false jsdom@30.1.3 @sinonjs/fake-timers@15.4.0
QUARTERMATE_MEASUREMENT_RUNTIME="$PWD/work/request-measurement-runtime" node scripts/measure-client-requests.mjs
```

이번 실행에서는 기존 릴리스 폴더의 node_modules를 읽기 전용 심볼릭 링크로 참조했다. 설치·빌드·소스 변경은 링크 대상에서 수행하지 않았다. jsdom과 fake-timers는 이 채팅의 격리된 work/request-measurement에 설치했다. 운영 인증정보를 주입하지 않았다.

12개 시나리오가 완료됐고 화면별 카운터·숨김·복귀·요청 겹침·오류 시 주기·저장 보호에 대한 검증이 통과했다. 스크립트 구문 검사 및 git diff --check도 통과했다. 앱 코드를 변경하지 않았으므로 전체 앱 회귀 검사를 재실행한 결과로 표현하지 않는다.

## 3단계 착수 범위

우선 팀 화면과 내 팀 화면의 동일 데이터 조회를 합치고, 복귀 이벤트와 정기 타이머가 겹쳐도 불필요한 추가 요청이 시작되지 않도록 한다. 저장 후에는 필요한 새 데이터를 다시 조회할 수 있어야 하므로 무조건 이전 요청을 재사용하지 않는다. 이전 요청의 응답을 버릴지, 저장 이후 한 번 더 조회할지를 구분한다.

3단계에서는 기존 3초/15초 주기와 위 보호장치를 검증 기준으로 유지하고 중복 제거 효과를 먼저 확인한다. 상황별 15초 갱신 변경은 5단계, 정적 파일 라우팅은 7단계에서 수행한다.
